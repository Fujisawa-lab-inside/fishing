# SeaBass 開発ワークフロー

## 1. まず探索系列を選ぶ

- A: 水理機構
- B: 地形と入力
- C: 釣り機能と表示

一つの作業で複数系列を同時に正本変更しない。系列間の接続が必要になった時点で統合候補として扱う。

## 2. 短いループを回す

1. 比較したい仮説を一文で書く。
2. 変更範囲を小さく保って実装する。
3. 同一 scenario と seed で短時間実行する。
4. 最小 smoke test、診断図、結果 JSON を確認する。
5. 良くなければ系列内で捨てる。良ければ次の反例条件を一つ試す。

探索中に、全回帰試験、全ファイル監査、YODA package、activation、公開手順を先回りして作らない。

## 3. 比較する

候補間で最低限、次を同じ表にする。

- scenario と seed
- 数値安全: negative / non-finite / mass balance / CFL
- 目的指標: その仮説が改善しようとした量
- simulated time と wall time
- 診断図または動画
- 既知の限界と適用外条件

## 4. 統合候補を選ぶ

同一条件で有利で、hard safety violation がなく、単一ケース依存でない候補だけを統合系列へ送る。この時点で、必要な物理観測・較正・独立検証の不足も明記する。

## 5. 採用後に固める

採用候補に対してだけ、次を必要範囲で実施する。

- 正本 Git への統合
- 詳細回帰試験と独立 review
- ADR と仕様更新
- 入力・source・成果物の SHA 固定
- YODA 長時間・多ケース検証
- physical validation
- GUI 昇格、釣行判断、公開 release の各別判定

一つの gate の合格を、後続 gate の合格として扱わない。

## 6. 現在の優先順位

1. 物理観測待ちだけを理由に探索を停止しない。
2. A・B・C で小さな比較を進め、見える機能進捗を増やす。
3. 物理未較正の結果は合成・診断として明示する。
4. 実観測 bundle が得られたら、既存の observation-intake validate-only 経路で検証する。
5. 統合候補が決まるまで、新しい監査基盤や authority 群を増やさない。
