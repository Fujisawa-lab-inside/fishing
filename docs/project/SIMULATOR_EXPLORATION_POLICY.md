# SeaBass シミュレータ探索開発方針

## 結論

SeaBass の開発を、**独立した探索系列 A・B・C** と、採用候補を固める **統合系列** に分離する。

- 探索中は、短い `edit -> run -> inspect` を優先する。
- 探索案は壊してよい。失敗した系列は、正本全体を修復せず破棄できるようにする。
- 詳細回帰試験、ADR、SHA 固定 package、YODA 多数試行、来歴監査、公開判定は、候補を選んだ後の統合系列で行う。
- 数値安全条件と、合成・診断・物理予測の表示区分は探索中も緩めない。

この分離は品質を下げるためではない。品質保証を、設計仮説がまだ頻繁に変わる段階から、採用候補が見えた段階へ移すためのものである。

## 四つの系列

### 探索 A: 水理機構

主な対象は、流束、wet/dry、河口堰、水頭差、魚道、境界条件、安定化手法である。短時間 canary と診断図で仮説を比較する。

### 探索 B: 地形と入力

主な対象は、河床・水深、メッシュ、河岸、潮位、流入量、気象・水文入力である。A と独立に差し替え可能な入力候補として扱う。

### 探索 C: 釣り機能と表示

主な対象は、流れのヨレ、ベイト、水温、タイドグラフ、キャスト候補、時間操作、GUI である。物理未較正データを用いる場合は、診断・合成表示であることを明示する。

### 統合系列

A・B・C の候補を同一 scenario、seed、時刻窓、比較指標で評価し、採用案を一つずつ選ぶ。採用後に初めて、正本統合、詳細回帰試験、来歴固定、YODA 長時間試験、GUI 昇格、公開判定を行う。

## 探索系列の共通最小契約

探索中に共通化するのは次だけとする。

1. 単位系: m、s、m/s、m3/s、JST/UTC の区別。
2. 入力: `scenario_id`、対象時刻窓、初期状態、境界入力。
3. 再現性: 明示した `seed`。乱数を使わない場合もその旨を記録する。
4. 最小結果 JSON: 系列、実装候補、status、simulated seconds、wall seconds、主要 metrics、生成物 path。
5. 比較指標: 数値安全、計算時間、目的指標、既知の限界。

探索候補の基本完了条件は次の四点である。

- ローカルで再実行できる。
- 対象機能の最小 smoke test が通る。
- 診断図または短い動画で挙動を確認できる。
- 比較可能な最小結果 JSON が出る。

探索中は、リポジトリ全体の回帰試験、全依存ファイルの SHA 固定、単回 activation、正式 authority、完全な provenance を毎回作らない。

## 統合へ進める条件

候補を統合系列へ移すのは、次を全て満たす場合とする。

- 同一条件で比較対象より明確な利点がある。
- 負水深、非有限値、質量収支破綻、許可していない逆流などの hard safety violation がない。
- 結果を診断、合成、物理候補、予測のどれとして扱うかが明確である。
- 既知の反例または別条件でも、利点が単一ケースだけの偶然ではないと確認できる。
- 統合で必要になる物理入力、観測、較正、公開条件の不足が列挙されている。

統合後は、候補に必要な範囲だけを対象に、詳細試験と監査を追加する。過去に作成した監査・観測 intake・YODA 証拠は削除せず、統合判定で再利用する。

## 計算資源

- Mac: 編集、短時間 canary、少数ケース比較、診断描画、GUI 確認。
- YODA: 長時間積分、多ケース sweep、Monte Carlo、高解像度生成、大規模回帰。
- YODA の実投入は、既存の安全条件と明示的な実行承認を維持する。package 準備と実行済みを混同しない。

## 現在の物理ゲートとの関係

実観測 bundle が不足していることは、探索 A・B・C を止める理由にはしない。ただし、物理予測、mesh 採用、釣行判断、GUI 昇格、公開 release の blocker であることは変わらない。

したがって現在は、合成・診断候補を速く比較できる。一方、それを「今日の遠賀川の予測」「釣れる場所」「物理的に正しい流れ」として昇格させてはならない。
